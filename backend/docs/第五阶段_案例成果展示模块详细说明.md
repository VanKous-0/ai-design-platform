# 第五阶段：案例成果展示模块详细说明

## 1. 模块定位

第五阶段实现的是案例成果展示模块，对应代码模块为 `modules.caseproject`。该模块定位为：

```text
案例展示 + 成果展示 + 阶段归类 + 工具关联 + 资源列表展示
```

当前第一版不做真实文件上传服务，不接 OSS、七牛云、MinIO 等外部存储。案例封面图和案例资源都只保存 URL 或本地路径字符串，先保证后端结构、前台展示和后台管理流程能跑通。

前台用户可以：

- 查询案例列表。
- 按设计阶段筛选案例。
- 按 AI 工具筛选案例。
- 按关键词搜索案例。
- 查看案例详情。
- 查看案例所属阶段。
- 查看案例主要关联工具。
- 查看案例资源列表。

管理员可以：

- 新增案例。
- 修改案例。
- 逻辑删除案例。
- 为案例新增资源。
- 修改案例资源。
- 逻辑删除案例资源。

## 2. 表结构说明

第五阶段新增两张表：

- `case_project`
- `case_asset`

### 2.1 `case_project`

`case_project` 是案例主表，用于保存案例的主体信息。

字段说明：

- `id`：主键 ID，用于唯一定位案例。详情接口和后台修改删除接口都使用该字段。
- `title`：案例标题，用于前台列表和详情页展示。
- `code`：案例稳定编码，数据库唯一，用于程序识别、数据迁移和后续维护。
- `stage_id`：所属工作流阶段 ID，逻辑关联 `workflow_stage.id`。
- `tool_id`：主要使用的 AI 工具 ID，可为空，逻辑关联 `ai_tool.id`。
- `cover_url`：案例封面图地址，用于列表卡片、详情头图等位置。
- `summary`：案例摘要，用于列表页展示简短说明。
- `content`：案例详细说明，用于详情页展示案例背景、过程、成果和工具使用说明。
- `source_desc`：案例来源或备注说明，用于标注测试数据、资料来源或整理说明。
- `author_name`：作者或整理人名称。
- `sort_order`：展示顺序，前台列表按该字段升序返回。
- `status`：启用状态，`1` 启用，`0` 禁用。前台只返回启用数据。
- `create_time`：创建时间。
- `update_time`：更新时间。
- `is_deleted`：逻辑删除标记，`0` 未删除，`1` 已删除。

为什么案例要和 `stage` 关联：

本项目围绕建筑设计全周期组织内容。案例不是孤立成果，而是对应某个设计阶段的参考材料。例如场地分析案例属于前期调研，概念生成案例属于概念设计，展板表达案例属于成果表达。通过 `stage_id` 关联工作流阶段，前台可以按阶段展示案例，后续复盘模块也能沿用同一条流程主线。

为什么案例可以选择性关联 `tool`：

一个案例可能主要体现某个 AI 工具在某个阶段的辅助价值，例如使用 DeepSeek 做场地分析，使用豆包做概念生成，使用 ChatGPT 做汇报文案整理。但并不是所有案例都必须明确绑定工具，所以 `tool_id` 允许为空。这样既能支持工具维度筛选，也保留普通案例展示的灵活性。

为什么 `code` 要唯一：

`title` 是展示文本，后续可能调整。`code` 是稳定标识，可用于数据初始化、前端映射、后续统计和迁移。唯一约束避免同一案例被重复配置。

### 2.2 `case_asset`

`case_asset` 是案例资源表，用于保存某个案例下的图片、文件等资源地址。

字段说明：

- `id`：主键 ID。
- `case_id`：所属案例 ID，逻辑关联 `case_project.id`。
- `asset_type`：资源类型，当前支持 `image` 和 `file`。
- `asset_url`：资源地址。第一版只是 URL 或路径字符串，不做真实上传。
- `title`：资源标题，用于前台展示。
- `description`：资源说明，用于解释该资源内容。
- `sort_order`：资源展示顺序。
- `create_time`：创建时间。
- `update_time`：更新时间。
- `is_deleted`：逻辑删除标记。

为什么案例主表和资源表要拆开：

一个案例通常会有多个资源，例如封面图、过程图、成果图、PDF、文档等。如果全部塞到 `case_project` 表里，会出现字段不断膨胀、资源数量不固定、排序困难的问题。拆成 `case_asset` 后，一个案例可以灵活关联任意数量的资源，并且每个资源可以单独维护标题、说明和顺序。

为什么封面图和资源图要分开考虑：

`cover_url` 是列表和详情入口展示使用的封面图，它服务于“快速识别案例”。`case_asset` 则是详情页中的资源列表，服务于“展示过程和成果”。封面图不一定要出现在资源列表中，资源图也不一定适合作为封面。

## 3. 案例、阶段、工具、资源之间的关系

当前关系如下：

```text
workflow_stage 1 ---- N case_project
ai_tool 0/1 ---- N case_project
case_project 1 ---- N case_asset
```

具体解释：

- 一个阶段可以有多个案例。
- 一个案例必须属于一个阶段。
- 一个案例可以选择性关联一个主要工具。
- 一个案例可以有多个资源。
- 删除案例时，当前服务会逻辑删除案例，并逻辑删除该案例下的资源。

当前 SQL 不使用数据库外键约束，而是通过索引、唯一约束和后端服务层校验维护关系，避免 DataGrip 对脚本解析产生无效红线。

## 4. 接口说明

### 4.1 前台接口

前台接口允许匿名访问。

#### 4.1.1 查询案例列表

```text
GET /api/cases
```

可选参数：

- `stageId`：按阶段筛选。
- `toolId`：按主要工具筛选。
- `keyword`：按关键词搜索，匹配 `title` 和 `summary`。

返回启用且未删除的案例列表，按 `sort_order ASC, id ASC` 返回。

#### 4.1.2 查询案例详情

```text
GET /api/cases/{id}
```

返回案例基本信息、所属阶段基本信息、关联工具基本信息和资源列表。

#### 4.1.3 查询案例资源列表

```text
GET /api/cases/{id}/assets
```

返回某个案例下的资源列表，按 `sort_order ASC, id ASC` 返回。

#### 4.1.4 推荐案例

```text
GET /api/cases/recommend?stageId=1
GET /api/cases/recommend?stageId=1&toolId=2
```

根据阶段推荐案例，可选按工具进一步筛选。

### 4.2 后台接口

后台接口需要 JWT 和 `ADMIN` 角色。

#### 4.2.1 新增案例

```text
POST /api/admin/cases
```

用于新增案例。`title`、`code`、`stageId` 必填，`toolId` 可为空。

#### 4.2.2 修改案例

```text
PUT /api/admin/cases/{id}
```

用于修改案例主体信息、封面图、摘要、详情、排序和状态。

#### 4.2.3 删除案例

```text
DELETE /api/admin/cases/{id}
```

执行逻辑删除。当前实现会同时逻辑删除该案例下的资源。

#### 4.2.4 新增案例资源

```text
POST /api/admin/cases/{id}/assets
```

为某个案例新增资源。当前资源类型只支持 `image` 和 `file`。

#### 4.2.5 修改案例资源

```text
PUT /api/admin/case-assets/{id}
```

修改资源类型、地址、标题、说明和排序。

#### 4.2.6 删除案例资源

```text
DELETE /api/admin/case-assets/{id}
```

逻辑删除某条资源。

## 5. 权限与安全

公开接口：

```text
GET /api/cases
GET /api/cases/{id}
GET /api/cases/{id}/assets
GET /api/cases/recommend
```

后台接口：

```text
POST /api/admin/cases
PUT /api/admin/cases/{id}
DELETE /api/admin/cases/{id}
POST /api/admin/cases/{id}/assets
PUT /api/admin/case-assets/{id}
DELETE /api/admin/case-assets/{id}
```

第五阶段只对 `SecurityConfig` 做了最小改动：放行前台案例查询接口。后台接口没有放行，继续走 JWT 和管理员权限校验。OpenAPI 配置也同步处理，前台案例接口不显示锁，后台接口保留鉴权要求。

## 6. 为什么第一版只存资源 URL

第一版的目标是先跑通案例展示和后台管理主流程，不做真实上传服务。真实上传会引入文件大小限制、文件类型校验、存储目录、访问权限、静态资源映射、云存储配置等额外问题。

当前先保存 URL 或路径字符串有几个好处：

1. 后端结构可以先稳定。
2. 前端可以先按 URL 展示图片和文件链接。
3. 后台管理接口可以先完成资源增删改。
4. 后续接本地上传或对象存储时，只需要替换资源 URL 的生成方式。

## 7. 当前数据说明

初始化 SQL 文件为：

```text
sql/case_init_data.sql
```

当前数据覆盖：

- 前期调研
- 概念设计
- 方案深化
- 成果表达

内容方向包括：

- 场地分析案例
- 概念生成案例
- 方案比选案例
- 平立剖深化案例
- 表达排版案例
- 汇报文案整理案例

当前资源路径都是测试占位路径，例如：

```text
/assets/cases/research-waterfront-cover.jpg
/assets/cases/presentation-board.pdf
```

这些路径只是开发和展示占位，不代表真实文件已经存在。

## 8. 后续正式定稿时建议修改的地方

正式定稿前建议重点维护：

- `title`：案例标题是否准确。
- `code`：案例编码是否稳定且唯一。
- `stage_id`：案例是否归属到正确阶段。
- `tool_id`：主要使用工具是否符合真实情况。
- `cover_url`：是否替换为真实封面图地址。
- `summary`：列表摘要是否简洁。
- `content`：详情说明是否完整。
- `source_desc`：来源或备注是否清楚。
- `author_name`：作者或整理人是否准确。
- `case_asset.asset_url`：资源地址是否替换为真实资源。
- `case_asset.asset_type`：资源类型是否正确。
- `sort_order`：前台展示顺序是否合理。
- `status`：是否只启用已确认案例。

如果只是暂时不展示某个案例，优先设置 `status = 0`。如果确认废弃，再调用删除接口做逻辑删除。
