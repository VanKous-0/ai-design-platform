# 第四阶段：提示词库模块详细说明

## 1. 模块定位

第四阶段实现的是提示词库模块，对应代码模块为 `modules.prompt`。该模块定位为：

```text
提示词管理 + 提示词检索 + 阶段归类 + 工具关联 + 前台展示
```

当前第一版不接外部 AI API，不在平台内直接调用模型生成内容。提示词正文、示例输入、示例输出、使用建议、所属阶段、推荐工具都由管理员手动维护。

前台用户可以：

- 查询提示词列表。
- 按阶段筛选提示词。
- 按分类筛选提示词。
- 按关键词搜索提示词。
- 查看提示词详情。
- 查看提示词所属阶段。
- 查看提示词推荐搭配的 AI 工具。
- 点击复制时触发 `copy_count + 1`。

管理员可以：

- 新增提示词。
- 修改提示词。
- 逻辑删除提示词。
- 设置某条提示词推荐搭配的工具。

## 2. 表结构说明

第四阶段新增两张表：

- `prompt_template`
- `prompt_tool_rel`

### 2.1 `prompt_template`

`prompt_template` 是提示词主体表，用于保存提示词的展示内容、分类、所属阶段、使用说明和复制次数。

字段说明：

- `id`：主键 ID，用于唯一定位提示词。详情接口和后台修改删除接口都使用该字段。
- `stage_id`：所属工作流阶段 ID，逻辑关联 `workflow_stage.id`。提示词按设计阶段组织，例如前期调研、概念设计、方案深化、成果表达。
- `title`：提示词标题，用于前台列表和详情页展示。
- `code`：提示词稳定编码，用于程序识别和后续维护，数据库唯一。
- `category`：提示词分类，例如“概念生成”“分析总结”“表达优化”“场地分析”等。
- `content`：提示词正文，是用户复制和使用的核心内容。
- `input_desc`：输入说明，告诉用户使用该提示词前需要准备什么资料。
- `output_desc`：输出说明，告诉用户使用该提示词后期望得到什么结果。
- `tips`：使用提示和注意事项，保存经验性提醒。
- `example_input`：示例输入，帮助前台用户理解如何填写上下文。
- `example_output`：示例输出，帮助用户理解结果形态。
- `sort_order`：展示顺序，列表按该字段升序返回。
- `copy_count`：复制次数，默认 0。前台调用复制接口后加 1。
- `status`：启用状态，`1` 启用，`0` 禁用。前台只返回启用数据。
- `create_time`：创建时间。
- `update_time`：更新时间。
- `is_deleted`：逻辑删除标记，`0` 未删除，`1` 已删除。

为什么提示词要和 `stage` 关联：

本项目是面向建筑设计全周期的平台。提示词不是孤立文本，而是服务于具体设计阶段。例如“场地条件分析提示词”适合前期调研，“设计概念生成提示词”适合概念设计，“成果说明压缩提示词”适合成果表达。通过 `stage_id` 关联工作流阶段，前端可以按阶段组织提示词，后续 AI 工具测评、案例、复盘模块也能围绕同一条流程主线联动。

为什么 `code` 要唯一：

`title` 是给人看的展示名称，后续可能改文案。`code` 是稳定标识，适合数据迁移、前端映射和后续模块配置使用。唯一约束可以避免同一提示词被重复配置。

为什么 `copy_count` 单独存储：

复制次数是提示词使用热度的基础指标。它不是实时计算字段，也不是日志字段。单独存储后，前台每次复制可以快速加 1，后续可以用于排序、热门提示词推荐或运营分析。

### 2.2 `prompt_tool_rel`

`prompt_tool_rel` 是提示词和 AI 工具之间的推荐关系表。

字段说明：

- `id`：主键 ID。
- `prompt_id`：提示词 ID，逻辑关联 `prompt_template.id`。
- `tool_id`：AI 工具 ID，逻辑关联 `ai_tool.id`。
- `create_time`：关系创建时间。

该表设置了 `prompt_id + tool_id` 唯一约束，避免同一提示词重复关联同一个工具。

为什么提示词和工具要用关系表：

一个提示词可能适合多个工具，例如“方案比选提示词”可以适合 DeepSeek、Kimi、ChatGPT。一个工具也可以适合多个提示词。如果把工具 ID 用逗号拼接到提示词表中，后续筛选、维护和查询都会变复杂，也不符合项目总纲要求。因此当前采用独立关系表表示多对多关系。

当前 SQL 没有使用数据库外键约束，而是采用普通索引、唯一约束和服务层校验。这样可以减少 DataGrip 对脚本内关联表的解析误报，同时后端在设置工具关系时会校验工具是否存在且启用。

## 3. 提示词、阶段、工具之间的关系

当前关系如下：

```text
workflow_stage 1 ---- N prompt_template
prompt_template N ---- N ai_tool
```

具体解释：

- 一个阶段可以有多条提示词。
- 一条提示词只属于一个阶段。
- 一条提示词可以推荐多个工具。
- 一个工具可以被多条提示词推荐。

例如：

- “场地条件分析提示词”属于“前期调研”阶段。
- 它可以推荐豆包、DeepSeek、ChatGPT 使用。
- 前台查看提示词详情时，会同时返回阶段信息和推荐工具列表。

## 4. 接口说明

### 4.1 前台接口

前台接口允许匿名访问。

#### 4.1.1 查询提示词列表

```text
GET /api/prompts
```

可选参数：

- `stageId`：按阶段筛选。
- `category`：按分类筛选。
- `keyword`：按关键词搜索，匹配 `title` 和 `content`。

返回启用且未删除的提示词列表，按 `sort_order ASC, id ASC` 返回。

#### 4.1.2 查询提示词详情

```text
GET /api/prompts/{id}
```

返回提示词主体内容、所属阶段基本信息和推荐工具列表。

#### 4.1.3 搜索提示词

```text
GET /api/prompts/search?keyword=场地
```

用于关键词搜索提示词。当前返回简化列表。

#### 4.1.4 推荐提示词

```text
GET /api/prompts/recommend?stageId=1
GET /api/prompts/recommend?stageId=1&toolId=2
```

根据阶段推荐提示词。可选 `toolId` 进一步筛选适合某个工具的提示词。

#### 4.1.5 复制提示词

```text
POST /api/prompts/{id}/copy
```

模拟前台复制提示词行为。接口会让 `copy_count + 1`，不要求登录。

### 4.2 后台接口

后台接口需要 JWT 和 `ADMIN` 角色。

#### 4.2.1 新增提示词

```text
POST /api/admin/prompts
```

用于新增提示词。`stageId`、`title`、`code`、`category`、`content` 必填。

#### 4.2.2 修改提示词

```text
PUT /api/admin/prompts/{id}
```

用于修改提示词主体内容、分类、排序、状态和示例内容。

#### 4.2.3 删除提示词

```text
DELETE /api/admin/prompts/{id}
```

执行逻辑删除。删除后前台不再返回该提示词。

#### 4.2.4 设置提示词推荐工具

```text
POST /api/admin/prompts/{id}/tools
```

当前实现是覆盖式更新。提交新的 `toolIds` 后，后端先删除该提示词旧的工具关联，再写入新的关联。

## 5. 权限与安全

公开接口：

```text
GET /api/prompts
GET /api/prompts/{id}
GET /api/prompts/search
GET /api/prompts/recommend
POST /api/prompts/{id}/copy
```

后台接口：

```text
POST /api/admin/prompts
PUT /api/admin/prompts/{id}
DELETE /api/admin/prompts/{id}
POST /api/admin/prompts/{id}/tools
```

第四阶段只对 `SecurityConfig` 做了最小改动：放行前台提示词接口。后台接口没有放行，继续走 JWT 和管理员权限校验。OpenAPI 配置也同步处理，前台提示词接口不显示锁，后台接口保留鉴权要求。

## 6. 为什么第一版不做平台内直接生成

根据项目总纲，第一版不接外部 AI API。提示词库模块的目标是帮助用户找到、理解和复制适合当前设计阶段的提示词，而不是在平台内直接调用模型。

这样设计的原因：

1. 降低实现复杂度，优先保证平台可运行、可展示、可维护。
2. 避免外部 API 鉴权、计费、限流和稳定性问题。
3. 当前大创项目更需要展示“工具选择和提示词组织能力”。
4. 提示词由管理员维护，更适合第一版快速落地和答辩展示。

## 8. 后续正式定稿时建议修改的地方

后续团队正式定稿时，建议重点维护：

- `title`：提示词标题是否适合前台展示。
- `category`：分类是否统一、清晰。
- `content`：提示词正文是否专业、可复制、可直接使用。
- `input_desc`：是否说明清楚用户需要准备什么。
- `output_desc`：是否说明清楚期望输出是什么。
- `tips`：是否补充了使用注意事项。
- `example_input` 和 `example_output`：是否贴近真实建筑设计场景。
- `stage_id`：是否归属到正确设计阶段。
- `prompt_tool_rel`：推荐工具是否符合实际使用经验。
- `sort_order`：前台展示顺序是否合理。
- `status`：是否只启用已确认内容。

如果只是暂时不展示某条提示词，优先设置 `status = 0`，不要直接删除。如果确认废弃，再使用后台删除接口做逻辑删除。
