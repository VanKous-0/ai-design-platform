# 第二阶段：工作流模块详细说明

## 1. 模块定位

### 1.1 第二阶段工作流模块在整个项目中的作用

第二阶段实现的是平台中的“建筑设计工作流”能力，对应代码模块为 `workflow`，核心对象是设计阶段 `stage` 和阶段下的工作流步骤 `step`。

在本项目中，工作流模块不是一个简单的静态菜单，而是后续业务内容的组织骨架。平台后续会围绕建筑设计全周期提供 AI 工具测评、提示词库、案例展示、复盘上传等能力，这些内容都需要知道自己属于哪个设计阶段、适合哪个环节、应该在流程中的什么位置展示。因此，工作流模块承担了“流程主线”的作用。

当前第二阶段已经实现：

- 前台查询设计阶段列表。
- 前台查询单个设计阶段详情。
- 前台查询某个设计阶段下的步骤列表。
- 后台新增、修改、删除设计阶段。
- 后台新增、修改、删除工作流步骤。
- 阶段和步骤的启用状态控制。
- 阶段和步骤的逻辑删除。
- 阶段和步骤按 `sort_order` 升序展示。

当前第二阶段没有实现：

- AI 工具测评模块。
- 提示词库模块。
- 案例展示模块。
- 复盘模块。
- 工作流步骤与其他模块的联动查询。
- 后台阶段和步骤分页列表接口。

这些内容属于后续阶段，不属于当前工作流模块已经完成的范围。

### 1.2 与第一阶段登录/JWT 模块的关系

第一阶段完成了项目基础骨架、统一返回体、全局异常处理、JWT 工具类、登录接口和当前用户接口。第二阶段工作流模块建立在第一阶段基础设施之上。

两者关系如下：

- 工作流接口统一使用第一阶段的 `Result` 返回格式。
- 工作流接口中的业务异常使用第一阶段的 `BusinessException` 和全局异常处理机制。
- 后台管理接口依赖第一阶段 JWT 鉴权链路，只有携带有效 token 的用户才能访问。
- 后台管理接口进一步通过 `@PreAuthorize("hasRole('ADMIN')")` 要求当前登录用户角色为 `ADMIN`。
- 前台展示接口不强制登录，便于网站首页或普通浏览页面直接读取流程数据。

也就是说，第一阶段提供“身份认证与通用基础能力”，第二阶段在这个基础上实现第一个正式业务模块。

### 1.3 在整个平台中的业务意义

本项目定位是“面向建筑设计全周期的生成式 AI 辅助决策服务平台”。这里的“全周期”需要在系统中有明确的结构表达，否则后续内容会变成一堆没有上下文的工具、提示词和案例。

工作流模块的业务意义主要体现在以下几个方面：

1. 建立设计流程主线  
   例如当前初始化数据中包含“前期调研、概念设计、方案深化、成果表达”等阶段。用户进入平台后，可以先理解建筑设计流程，再进入具体内容。

2. 为后续模块提供归属关系  
   后续 AI 工具可以标注适用于哪个阶段，提示词可以按阶段分类，案例可以展示它主要对应哪个阶段，复盘记录也可以关联用户正在处理的设计阶段。

3. 支持后台维护  
   工作流不是写死在前端代码里的。管理员可以通过后台接口维护阶段和步骤，使项目在答辩或后续迭代时能调整流程内容。

4. 支持前台稳定展示  
   前台展示接口只返回启用且未删除的数据，避免后台临时编辑或停用的数据直接影响用户端展示。

### 1.4 前台公开接口和后台管理接口的职责

当前实现把工作流接口分成两类：前台公开接口和后台管理接口。

前台公开接口：

- 路径以 `/api/stages` 开头。
- 当前在 `SecurityConfig` 中匿名放行。
- 只返回 `status = 1` 且未逻辑删除的数据。
- 主要用于前端页面展示设计阶段和工作流步骤。

后台管理接口：

- 路径以 `/api/admin` 开头。
- 必须携带 JWT token。
- 当前通过 `@PreAuthorize("hasRole('ADMIN')")` 限制管理员访问。
- 用于新增、修改、删除阶段和步骤。
- 可以维护 `status`，从而控制数据是否出现在前台。

这种划分保证了前台展示简单稳定，后台维护受权限保护。

## 2. 核心概念说明

### 2.1 什么是 stage（阶段）

`stage` 表示建筑设计流程中的一个大的阶段。它不是具体的一件任务，而是对一组相关任务的归类。

例如当前初始化数据中有：

- 前期调研
- 概念设计
- 方案深化
- 成果表达

“前期调研”本身不是一个动作，而是一个阶段。它可能包含场地信息整理、案例与规范调研等多个步骤。前端可以把阶段展示为流程导航、阶段卡片、阶段详情页或筛选条件。

在数据库中，阶段由 `workflow_stage` 表保存。阶段有 `name` 用于展示，有 `code` 用于程序识别，有 `sort_order` 用于控制展示顺序，有 `status` 和 `is_deleted` 用于控制可见性。

### 2.2 什么是 step（步骤）

`step` 表示某个设计阶段下面更具体的工作步骤。它描述的是“在这个阶段具体要做什么、输入是什么、输出是什么、有什么注意事项”。

例如“前期调研”阶段下面可以有：

- 场地信息整理
- 案例与规范调研

“概念设计”阶段下面可以有：

- 设计概念生成
- 空间策略推演

步骤比阶段更细。前台展示时，用户通常会先看到阶段，再展开阶段下的步骤。后续提示词、工具推荐、案例说明都可以围绕步骤进一步细化。

在数据库中，步骤由 `workflow_step` 表保存。步骤通过 `stage_id` 关联到所属阶段。

### 2.3 stage 和 step 的关系

当前实现中，`stage` 和 `step` 是一对多关系：

- 一个 `workflow_stage` 可以有多个 `workflow_step`。
- 一个 `workflow_step` 只属于一个 `workflow_stage`。

例如：

```text
前期调研 stage
├── 场地信息整理 step
└── 案例与规范调研 step

概念设计 stage
├── 设计概念生成 step
└── 空间策略推演 step
```

数据库层面通过 `workflow_step.stage_id` 关联 `workflow_stage.id`，并且建表 SQL 中设置了外键约束：

```sql
CONSTRAINT `fk_workflow_step_stage`
    FOREIGN KEY (`stage_id`) REFERENCES `workflow_stage` (`id`)
```

这可以避免创建一个指向不存在阶段的步骤。

### 2.4 为什么拆成两张表

阶段和步骤必须拆成两张表，原因不是形式上的“规范化”，而是业务结构本身不同。

如果把阶段和步骤放在一张表里，会出现几个问题：

1. 字段含义混乱  
   阶段有 `name`、`code`、`description`，步骤有 `title`、`content`、`input_desc`、`output_desc`、`tips`。如果放在一张表里，有些字段只对阶段有意义，有些字段只对步骤有意义。

2. 难以表达一对多关系  
   一个阶段下面有多个步骤。拆表后可以清晰表达“阶段是一组步骤的容器”。如果放在一张表里，就需要用父子结构或冗余字段，后续查询和维护更复杂。

3. 后续扩展不清晰  
   后续 AI 工具、提示词、案例可能关联阶段，也可能进一步关联步骤。拆成两张表后，其他模块可以明确选择关联 `stage_id` 或 `step_id`。

4. 后台维护更自然  
   管理员维护阶段和维护步骤是两类操作。阶段控制流程大结构，步骤控制某一阶段内的具体内容。

因此当前实现采用：

- `workflow_stage`：保存设计阶段。
- `workflow_step`：保存阶段下的步骤。

### 2.5 为什么要有 sort_order

`sort_order` 是业务排序字段，用于控制前台展示顺序。

不能依赖 `id` 排序。`id` 只表示数据库插入顺序，不代表业务顺序。比如后续团队发现“成果表达”应该放到更靠后，或者在“概念设计”和“方案深化”之间新增“方案比选”，如果依赖 `id`，排序会非常被动。

使用 `sort_order` 的好处：

- 管理员可以调整显示顺序。
- 新增阶段时可以插入到中间位置。
- 前端不需要自己写死排序逻辑。
- 数据库查询可以稳定按业务顺序返回。

当前代码中：

- 阶段列表按 `sort_order ASC, id ASC` 查询。
- 步骤列表按 `sort_order ASC, id ASC` 查询。
- 当 `sort_order` 相同时，使用 `id` 作为辅助排序，保证结果稳定。

### 2.6 为什么除了 name 之外还要有 code

`name` 是给人看的名称，`code` 是给程序识别的稳定编码。

例如：

```text
name: 前期调研
code: RESEARCH
```

`name` 可能因为展示文案调整而变化，比如“前期调研”改成“前期研究与调研”。如果后续代码、前端路由、数据导入、统计逻辑都依赖中文名称，就会因为名称变化导致联动问题。

`code` 的作用是提供一个稳定标识：

- 后续模块可以按 `code` 做配置或映射。
- 前端可以根据 `code` 做图标、颜色、展示逻辑。
- 数据初始化和数据迁移更稳定。
- 管理员修改 `name` 时不影响程序识别。

当前数据库对 `workflow_stage.code` 加了唯一索引 `uk_workflow_stage_code`，代码层也在创建和更新阶段时检查编码唯一性。

### 2.7 为什么删除使用逻辑删除

当前项目优先使用逻辑删除，而不是物理删除。

逻辑删除的意思是：删除时不真正从数据库移除记录，而是把 `is_deleted` 从 `0` 改成 `1`。MyBatis-Plus 会根据实体上的 `@TableLogic` 自动处理逻辑删除条件。

使用逻辑删除的原因：

1. 保留历史数据  
   工作流数据后续可能被工具、提示词、案例、复盘记录引用。如果直接物理删除，相关数据会失去上下文。

2. 避免误删造成不可恢复  
   管理员维护时可能误操作。逻辑删除更容易恢复。

3. 便于审计和排查  
   当某个阶段或步骤突然不展示时，可以通过数据库检查是否被逻辑删除，而不是完全找不到记录。

4. 符合项目总纲要求  
   指导总纲明确要求优先逻辑删除，不轻易物理删除。

当前实现中：

- `WorkflowStage.isDeleted` 使用 `@TableLogic`。
- `WorkflowStep.isDeleted` 使用 `@TableLogic`。
- 删除阶段时会逻辑删除阶段，并逻辑删除该阶段下的步骤。
- 删除步骤时只逻辑删除该步骤。

## 3. 数据库表详细说明

### 3.1 `workflow_stage` 表

#### 3.1.1 表的作用

`workflow_stage` 用于保存建筑设计流程中的阶段信息。它是工作流模块的一级结构，也是后续模块进行阶段归类的基础。

当前初始化数据包含：

- `RESEARCH`：前期调研
- `CONCEPT`：概念设计
- `DEVELOPMENT`：方案深化
- `PRESENTATION`：成果表达

#### 3.1.2 字段详细说明

##### `id`

`id` 是阶段表的主键，由数据库自增生成。它用于唯一定位一条阶段记录。

业务中，前端访问阶段详情使用：

```text
GET /api/stages/{id}
```

后端查询步骤列表也通过阶段 `id` 关联：

```text
GET /api/stages/{id}/steps
```

需要注意：`id` 不应该被当作业务排序依据，也不应该作为对外长期稳定的业务编码。它只是数据库层面的唯一标识。

##### `name`

`name` 是阶段名称，主要用于前台展示。

例如：

```text
前期调研
概念设计
方案深化
成果表达
```

前端页面展示阶段卡片、流程导航、阶段详情标题时使用 `name`。后台创建和修改阶段时，`name` 是必填项，当前 DTO 使用 `@NotBlank` 校验。

##### `code`

`code` 是阶段编码，主要用于程序识别和后续模块稳定关联。

例如：

```text
RESEARCH
CONCEPT
DEVELOPMENT
PRESENTATION
```

`code` 的意义在于稳定。`name` 可以改展示文案，但 `code` 应尽量保持不变。当前数据库对 `code` 建了唯一索引，后端服务层也检查同一个 `code` 不能重复。

后续如果 AI 工具测评模块需要按阶段推荐工具，可以使用 `stage_id` 关联，也可以在配置层面参考 `code` 做稳定识别。

##### `description`

`description` 是阶段说明，用于解释这个阶段的目标、范围和主要任务。

例如“前期调研”的说明是：

```text
收集场地、用户、政策、案例等基础信息，形成设计依据。
```

这个字段主要用于阶段详情页或阶段卡片补充说明。它不是程序控制字段，而是内容展示字段。当前允许为空，便于后台先创建阶段，再逐步补充说明。

##### `sort_order`

`sort_order` 是阶段展示顺序字段。数值越小，越靠前展示。

当前初始化数据使用：

```text
10 前期调研
20 概念设计
30 方案深化
40 成果表达
```

这种间隔设置方便后续在中间插入新阶段。例如要在“概念设计”和“方案深化”之间插入“方案比选”，可以设置 `sort_order = 25`。

当前前台阶段列表查询按：

```text
sort_order ASC, id ASC
```

##### `status`

`status` 是启用状态字段。

当前约定：

- `1`：启用
- `0`：禁用

前台展示接口只查询 `status = 1` 的数据。后台可以通过修改 `status` 来临时隐藏某个阶段，而不需要删除它。

例如，一个阶段还没有编辑完整时，可以设置 `status = 0`，这样它不会出现在前台列表中。

##### `create_time`

`create_time` 是记录创建时间。

它主要用于后台管理、数据排查和后续审计。当前建表 SQL 设置默认值为 `CURRENT_TIMESTAMP`，后端创建阶段时也会设置当前时间。

前台 VO 当前会返回 `createTime`，但它不是前台展示的核心字段。

##### `update_time`

`update_time` 是记录最近更新时间。

当后台修改阶段名称、说明、排序或状态时，这个字段会更新。建表 SQL 中设置了：

```sql
ON UPDATE CURRENT_TIMESTAMP
```

后端更新阶段时也会设置 `LocalDateTime.now()`。

这个字段便于判断后台内容最后一次维护时间。

##### `is_deleted`

`is_deleted` 是逻辑删除字段。

当前约定：

- `0`：未删除
- `1`：已删除

实体类中使用 `@TableLogic`，MyBatis-Plus 会自动在常规查询中追加未删除条件，并在调用 `deleteById` 时执行逻辑删除。

业务上，删除阶段不是真正移除数据库记录，而是将其标记为已删除。当前实现中删除阶段时，也会逻辑删除该阶段下的步骤。

#### 3.1.3 字段分类

展示字段：

- `name`
- `description`
- `sort_order`

程序识别字段：

- `id`
- `code`

管理控制字段：

- `status`
- `is_deleted`
- `create_time`
- `update_time`

必填字段：

- `id`
- `name`
- `code`
- `sort_order`
- `status`
- `create_time`
- `update_time`
- `is_deleted`

扩展和维护字段：

- `description`
- `status`
- `sort_order`
- `create_time`
- `update_time`
- `is_deleted`

### 3.2 `workflow_step` 表

#### 3.2.1 表的作用

`workflow_step` 用于保存某个设计阶段下的具体工作步骤。它是工作流模块的二级结构。

例如“前期调研”阶段下有：

- 场地信息整理
- 案例与规范调研

步骤数据用于前台展示某个阶段具体该做什么，也为后续提示词推荐、工具推荐和案例展示提供更细的业务锚点。

#### 3.2.2 字段详细说明

##### `id`

`id` 是步骤表主键，由数据库自增生成。

后台修改或删除步骤时使用步骤 `id` 定位具体记录：

```text
PUT /api/admin/steps/{id}
DELETE /api/admin/steps/{id}
```

同样，`id` 只是数据库唯一标识，不代表业务顺序。

##### `stage_id`

`stage_id` 表示步骤所属的阶段，对应 `workflow_stage.id`。

这是 `workflow_stage` 和 `workflow_step` 之间关系的关键字段。没有 `stage_id`，步骤就无法知道自己属于哪个阶段。

当前建表 SQL 对它设置了外键约束，防止步骤关联到不存在的阶段。当前服务层在新增和更新步骤时也会先调用 `getStageEntity(stageId)` 检查阶段是否存在。

##### `title`

`title` 是步骤标题，用于前台展示步骤名称。

例如：

```text
场地信息整理
案例与规范调研
设计概念生成
空间策略推演
```

后台创建和修改步骤时，`title` 是必填项，当前 DTO 使用 `@NotBlank` 校验。

##### `content`

`content` 是步骤正文内容，用于说明这个步骤具体要做什么。

例如：

```text
整理基地位置、周边交通、自然条件、历史文脉和限制条件。
```

它是步骤最核心的展示内容，前台步骤详情、流程说明、学习引导都可以使用这个字段。当前 DTO 对 `content` 使用 `@NotBlank` 校验，保证步骤不能只有标题没有内容。

##### `input_desc`

`input_desc` 是输入说明，用于描述执行这个步骤前需要准备什么材料或信息。

例如：

```text
场地照片、测绘资料、规划条件、任务书
```

这个字段帮助用户理解“做这个步骤之前需要什么”。后续如果和提示词模块联动，也可以把 `input_desc` 作为生成提示词时的上下文参考。

##### `output_desc`

`output_desc` 是输出说明，用于描述完成这个步骤后应该得到什么成果。

例如：

```text
场地分析要点清单
```

这个字段帮助用户理解每一步的交付物。对于建筑设计流程来说，明确输入和输出比只列任务标题更有指导价值。

##### `tips`

`tips` 是提示与注意事项。

例如：

```text
注意区分客观条件和主观判断。
```

这个字段用于保存经验性提醒、容易踩坑的点、设计判断注意事项等。它不直接参与程序控制，但能提升前台内容的实用性。

##### `sort_order`

`sort_order` 是步骤在同一阶段下的展示顺序。

例如在“前期调研”阶段中：

```text
10 场地信息整理
20 案例与规范调研
```

当前查询某个阶段步骤时按：

```text
sort_order ASC, id ASC
```

这样同一个阶段下的步骤可以按真实工作顺序展示。

##### `status`

`status` 是步骤启用状态。

当前约定：

- `1`：启用
- `0`：禁用

前台步骤列表只返回 `status = 1` 的步骤。后台可以将某个步骤设为禁用，让它暂时不出现在前台，但保留数据以便后续恢复。

##### `create_time`

`create_time` 是步骤创建时间，用于记录后台第一次创建该步骤的时间。

它对前台展示不是核心字段，但对后台维护和排查数据很有用。例如判断某条步骤是否是初始化数据，或者是后续管理员新增的内容。

##### `update_time`

`update_time` 是步骤最近更新时间。

当后台修改步骤标题、内容、输入输出说明、提示、排序或状态时，这个字段会更新。它用于维护追踪和后续审计。

##### `is_deleted`

`is_deleted` 是逻辑删除字段。

当前约定：

- `0`：未删除
- `1`：已删除

实体类中使用 `@TableLogic`。后台删除步骤时调用 `deleteById`，实际执行逻辑删除。前台查询不会返回逻辑删除的数据。

#### 3.2.3 字段分类

展示字段：

- `content`
- `input_desc`
- `output_desc`
- `tips`

程序识别字段：

管理控制字段：

必填字段：

- `title`

- `sort_order`
- `status`
- `create_time`
- `update_time`
- `is_deleted`

扩展和维护字段：

- `input_desc`

- `tips`
- `status`
- `sort_order`

### 3.3 表之间的关系

`workflow_stage` 和 `workflow_step` 是一对多关系。

数据库关系：

```text
workflow_stage.id 1 ---- N workflow_step.stage_id
```

业务关系：

- 一个阶段可以包含多个步骤。
- 一个步骤必须属于一个阶段。
- 查询阶段步骤时，使用 `workflow_step.stage_id = workflow_stage.id`。
- 删除阶段时，当前服务实现会逻辑删除该阶段和该阶段下所有步骤。

## 5. 权限与安全说明

### 5.1 公开接口

当前公开接口是：

```text
GET /api/stages
GET /api/stages/{id}
GET /api/stages/{id}/steps
```

它们在 `SecurityConfig` 中通过以下配置匿名放行：

```java
.requestMatchers(HttpMethod.GET, "/api/stages", "/api/stages/*", "/api/stages/*/steps").permitAll()
```

公开原因：

- 这些接口用于前台页面展示。
- 数据内容是平台公开流程说明，不涉及用户隐私。
- 匿名访问有利于首页、流程页、未登录用户浏览。

### 5.2 后台管理接口

当前后台管理接口是：

```text
POST /api/admin/stages
PUT /api/admin/stages/{id}
DELETE /api/admin/stages/{id}
POST /api/admin/steps
PUT /api/admin/steps/{id}
DELETE /api/admin/steps/{id}
```

这些接口没有在 `SecurityConfig` 中放行，因此必须先通过 JWT 鉴权。并且 `AdminWorkflowController` 上有：

```java
@PreAuthorize("hasRole('ADMIN')")
```

这表示登录用户必须具备 `ADMIN` 角色。

### 5.3 后台接口为什么必须带 token

后台接口会修改数据库中的流程主数据。如果任何人都能调用，就可能导致：

- 阶段被恶意删除。
- 步骤内容被篡改。
- 前台流程展示异常。
- 后续模块关联关系混乱。

因此后台接口必须要求登录，并且必须限制管理员角色。

### 5.4 当前鉴权链路如何工作

当前项目的鉴权链路如下：

1. 用户调用 `POST /api/auth/login`，提交用户名和密码。
2. 后端校验 `sys_user` 中的用户和密码。
3. 登录成功后返回 JWT token。
4. 前端或 Knife4j 在请求头中携带：

```text
Authorization: Bearer <token>
```

5. `JwtAuthenticationFilter` 解析 token。
6. 解析成功后，将用户 ID 和角色写入 Spring Security 上下文。
7. 后台接口进入方法前，`@PreAuthorize("hasRole('ADMIN')")` 检查角色。

当前初始化管理员用户角色为 `ADMIN`，JWT 过滤器中会转换为 Spring Security 权限 `ROLE_ADMIN`。

### 5.5 第二阶段对 SecurityConfig 的处理

第二阶段只做了最小安全配置变更：

- 增加前台工作流 `GET` 接口匿名放行。
- 没有放行 `/api/admin/**`。
- 没有修改登录和 JWT 的业务逻辑。
- 没有改变文档接口放行策略。

### 5.6 为什么前台可以匿名而后台不能

前台接口只读取已经启用、未删除的流程展示数据，本质是公开内容。后台接口会创建、修改、删除流程主数据，属于管理能力。

因此权限策略是：

- 读公开流程：允许匿名。
- 写流程配置：必须登录并且必须是管理员。

## 6. 测试与验收过程说明

### 6.1 数据库层面需要验证什么

数据库层面主要验证：

1. `workflow_stage` 表能正常创建。
2. `workflow_step` 表能正常创建。
3. `workflow_step.stage_id` 外键能关联到 `workflow_stage.id`。
4. 初始化数据能正常插入。
5. `workflow_stage.code` 唯一索引生效。
6. `status`、`sort_order`、`is_deleted` 字段存在且默认值合理。

建议执行：

```sql
SELECT id, name, code, sort_order, status, is_deleted
FROM workflow_stage
ORDER BY sort_order ASC;

SELECT id, stage_id, title, sort_order, status, is_deleted
FROM workflow_step
ORDER BY stage_id ASC, sort_order ASC;
```

### 6.2 前台接口测试了什么

前台接口应测试：

- `GET /api/stages` 是否无需 token 可以访问。
- 返回阶段是否按 `sortOrder` 升序。
- 返回数据是否只包含启用阶段。
- `GET /api/stages/1` 是否能返回阶段详情。
- `GET /api/stages/1/steps` 是否能返回该阶段下启用步骤。
- 步骤列表是否按 `sortOrder` 升序。

这些测试说明前台展示能力已经具备。

### 6.3 后台接口测试了什么

后台接口应测试：

- 不带 token 调用 `/api/admin/...` 是否被拒绝。
- 带普通用户 token 是否被角色限制拒绝。
- 带管理员 token 是否能新增、修改、删除阶段。
- 带管理员 token 是否能新增、修改、删除步骤。
- 请求体参数缺失时是否触发 Jakarta Validation。

这些测试说明后台管理能力和权限控制已经具备。

### 6.4 唯一性校验测试了什么

当前唯一性校验主要针对 `workflow_stage.code`。

测试方式：

1. 创建一个阶段，`code = TEST_STAGE`。
2. 再次创建另一个阶段，仍然使用 `code = TEST_STAGE`。
3. 后端服务层会返回业务错误“阶段编码已存在”。
4. 即使绕过服务层，数据库唯一索引 `uk_workflow_stage_code` 也会阻止重复数据。

这说明 `code` 的稳定唯一性得到保障。

### 6.5 逻辑删除测试了什么

逻辑删除应测试：

- 调用 `DELETE /api/admin/stages/{id}` 后，数据库记录仍存在。
- 被删除阶段的 `is_deleted` 变为 `1`。
- 该阶段下步骤的 `is_deleted` 也变为 `1`。
- 前台 `GET /api/stages` 不再返回该阶段。
- 前台 `GET /api/stages/{id}/steps` 不再返回该阶段下步骤。

步骤删除应测试：

- 调用 `DELETE /api/admin/steps/{id}` 后，数据库记录仍存在。
- 该步骤 `is_deleted` 变为 `1`。
- 前台步骤列表不再展示该步骤。

这些测试说明删除策略符合项目总纲中的逻辑删除要求。

### 6.6 sort_order 排序测试了什么

排序测试应验证：

- 阶段列表不是按 `id` 排序，而是按 `sort_order` 排序。
- 同一个阶段下的步骤不是按 `id` 排序，而是按 `sort_order` 排序。
- 当两个数据 `sort_order` 相同时，按 `id` 辅助排序，保证返回顺序稳定。

测试方法：

1. 新增两个阶段，设置不同 `sortOrder`。
2. 调用 `GET /api/stages`。
3. 检查返回顺序是否按 `sortOrder` 升序。
4. 对步骤执行同样测试。

### 6.7 stage 和 step 的增删改查如何验证

阶段验证：

- 查：`GET /api/stages`、`GET /api/stages/{id}`。
- 增：`POST /api/admin/stages`。
- 改：`PUT /api/admin/stages/{id}`。
- 删：`DELETE /api/admin/stages/{id}`。

步骤验证：

- 查：`GET /api/stages/{id}/steps`。
- 增：`POST /api/admin/steps`。
- 改：`PUT /api/admin/steps/{id}`。
- 删：`DELETE /api/admin/steps/{id}`。

注意当前没有单独的后台列表接口，例如 `GET /api/admin/stages` 或 `GET /api/admin/steps`。后台验证新增和修改后的结果，可以先通过前台公开接口查看启用数据，也可以直接在数据库中查询。

### 6.8 哪些测试结果说明第二阶段通过

满足以下结果即可认为第二阶段工作流模块通过：

- SQL 执行成功，两张表和初始化数据存在。
- 项目可以正常编译并启动。
- `GET /api/stages` 匿名访问成功。
- `GET /api/stages/{id}` 能返回启用阶段详情。
- `GET /api/stages/{id}/steps` 能返回启用步骤列表。
- 后台接口不带 token 不能访问。
- 管理员 token 可以新增、修改、删除阶段和步骤。
- 重复阶段 `code` 会被拒绝。
- 删除后数据不再出现在前台，但数据库中保留 `is_deleted = 1`。
- 修改 `sort_order` 后前台返回顺序发生对应变化。

## 7. 当前模块局限与后续扩展方向

### 7.1 当前数据是测试/初始化数据

当前 `workflow_init_data.sql` 中的数据主要用于开发、联调和展示最小可用流程，不代表最终定稿内容。

这些数据包括：

- 前期调研
- 概念设计
- 方案深化
- 成果表达

以及每个阶段下的若干测试步骤。后续团队确定正式建筑设计流程后，可以通过后台接口或 SQL 修改这些数据。

### 7.2 正式流程确定后如何维护数据

建议维护顺序：

1. 先确定阶段结构。
2. 为每个阶段确定稳定 `code`。
3. 设置阶段 `sort_order`。
4. 再补充每个阶段下的步骤。
5. 为步骤设置 `sort_order`。
6. 确认 `status = 1` 后再前台展示。

如果只是修改展示文案，优先修改：

- `name`
- `description`
- `title`
- `content`
- `input_desc`
- `output_desc`
- `tips`

如果是调整展示顺序，优先修改：

- `sort_order`

如果只是暂时隐藏，不要删除，优先修改：

- `status = 0`

### 7.3 后续会联动的模块

#### AI 工具测评模块

后续 AI 工具可以关联设计阶段，例如某工具适用于“概念设计”或“成果表达”。工作流阶段会成为工具推荐和筛选的重要条件。

#### 提示词库模块

提示词可以按阶段归类，例如“前期调研提示词”“概念生成提示词”“成果表达提示词”。用户查看某阶段步骤时，可以进一步看到相关提示词。

#### 案例展示模块

案例可以标记对应的设计阶段或展示其在不同阶段的成果。工作流模块为案例提供流程上下文。

#### 复盘模块

用户上传复盘时，可以选择关联某个设计阶段。这样后台可以统计用户在哪些阶段使用了哪些工具、遇到了什么问题。

### 7.4 后续可能继续优化的地方

当前工作流模块已经满足第二阶段目标，但仍有可优化方向：

- 增加后台阶段列表接口，支持后台管理页展示全部数据，包括禁用数据。
- 增加后台步骤列表接口，支持按阶段查看全部步骤，包括禁用数据。
- 对 `status` 增加枚举或校验，限制只能为 `0` 或 `1`。
- 增加 `create_by`、`update_by` 字段，记录管理员操作人。
- 增加更细的权限控制，例如普通管理员和超级管理员。
- 支持批量调整排序。
- 支持阶段下步骤数量统计。
- 支持前台一次性返回阶段和步骤的树形结构。

这些优化不属于当前第二阶段必须范围，可以在后续管理后台完善时逐步补充。

## 8. 给后续开发者的建议

### 8.1 最容易混淆的点

最容易混淆的是 `stage` 和 `step` 的职责。

`stage` 是大的阶段，例如“概念设计”。  
`step` 是阶段下的具体任务，例如“设计概念生成”。

不要把所有流程内容都塞进 `workflow_stage.description`，也不要把阶段当成步骤来创建。阶段负责流程结构，步骤负责具体执行内容。

### 8.2 不要把 id 当排序字段

`id` 是数据库自增主键，只能说明插入先后，不能说明业务先后。

例如后续新增“方案比选”阶段，它可能应该排在“概念设计”和“方案深化”之间，但它的 `id` 一定比旧数据大。如果按 `id` 排序，它只能排到最后，业务顺序就错了。

因此排序必须使用 `sort_order`。

### 8.3 code 要尽量稳定且唯一

`code` 是程序识别用的稳定编码。修改 `name` 通常问题不大，但随意修改 `code` 可能影响后续模块联动。

建议：

- `code` 使用英文大写和下划线。
- 一旦被前端或后续模块依赖，不要随便改。
- 如果只是改展示名称，改 `name`，不要改 `code`。

### 8.4 不要直接物理删除数据

工作流数据后续会被工具、提示词、案例和复盘引用。如果直接物理删除，相关模块可能只剩一个失效的 `stage_id` 或 `step_id`。

当前系统使用 `is_deleted` 逻辑删除。后续维护时应继续遵守这个策略。

如果只是暂时不想展示，优先使用：

```text
status = 0
```

如果确认不再使用，再调用删除接口进行逻辑删除。

### 8.5 修改 workflow 数据时优先改什么

根据目的选择字段：

- 改展示名称：改 `name` 或 `title`。
- 改解释内容：改 `description`、`content`、`input_desc`、`output_desc`、`tips`。
- 改展示顺序：改 `sort_order`。
- 临时隐藏：改 `status = 0`。
- 长期移除：调用删除接口，进行逻辑删除。
- 稳定标识：谨慎修改 `code`。

### 8.6 前后端联调注意事项

前台联调：

- `GET /api/stages` 不需要 token。
- `GET /api/stages/{id}` 不需要 token。
- `GET /api/stages/{id}/steps` 不需要 token。
- 前端应使用 `sortOrder` 展示顺序，但通常后端已经排好序。
- 前端不要依赖 `id` 判断阶段类型，展示类型可优先参考 `code`。

后台联调：

- 后台接口必须先登录拿 token。
- Knife4j 中授权时请求头应为 `Authorization`。
- token 值格式为 `Bearer <accessToken>`。
- 后台接口需要管理员角色。
- 创建和更新请求体字段使用驼峰命名，如 `sortOrder`、`stageId`、`inputDesc`。

## 9. 建议后续如何维护初始化 SQL

当前初始化 SQL 文件是：

```text
sql/workflow_init_data.sql
```

它使用固定 `id` 和 `ON DUPLICATE KEY UPDATE`，适合开发阶段重复执行。

后续维护建议：

1. 开发期可以继续维护这个文件，保证新同学拉项目后能快速得到测试数据。
2. 正式内容确定后，把初始化数据改成团队确认过的流程内容。
3. 不建议在初始化 SQL 中随意删除旧数据；如果要废弃数据，可以更新 `status` 或 `is_deleted`。
4. 如果线上已有真实数据，后续变更应单独写迁移 SQL，不要直接覆盖初始化 SQL。
5. 初始化 SQL 中的 `code` 应保持稳定，避免后续模块引用失效。
