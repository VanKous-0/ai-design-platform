# 第七阶段：首页内容模块详细说明

## 一、模块定位

第七阶段首页内容模块是当前后端主线的最后一个业务模块，负责把首页展示所需的文案、图片路径、跳转链接和获奖/成果信息从代码中抽离出来，交给数据库和后台接口维护。

本模块不重做登录/JWT、工作流、AI 工具测评、提示词库、案例展示、复盘模块，而是在前六阶段基础上增加首页聚合展示能力。首页可以作为前端进入平台的第一屏入口，把已有模块以区块形式组织起来，例如工作流入口、工具测评入口、提示词库入口、案例入口和复盘入口。

第一版不做真实文件上传，也不接 OSS、七牛云、MinIO 等外部存储。`image_url`、`link_url` 只保存 URL 或路径字符串，后续正式部署时可以替换为真实静态资源地址或前端路由。

## 二、数据库表说明

### 1. site_content

`site_content` 用于保存首页内容区块。它不是文章系统，也不是复杂 CMS，只是为首页展示提供可维护的数据来源。

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `id` | 主键 ID | 数据库内部唯一标识，接口详情、修改、删除时使用 |
| `section_key` | 首页区块标识 | 程序识别字段，例如 `hero`、`intro`、`workflow_entry`、`contact` |
| `title` | 区块标题 | 前台展示的主要标题 |
| `subtitle` | 区块副标题 | 前台展示的辅助说明 |
| `content` | 区块正文 | 保存较长的介绍、说明或展示文案 |
| `image_url` | 图片 URL 或路径 | 第一版只记录字符串，不负责文件上传 |
| `link_url` | 跳转链接 | 可指向前端路由、后端接口或外部说明页 |
| `extra_json` | 扩展 JSON 字符串 | 预留按钮文案、标签、卡片副信息等结构化展示数据；数据库按文本保存，后端按字符串返回 |
| `sort_order` | 排序号 | 控制同一类区块或列表中的展示顺序，越小越靠前 |
| `status` | 启用状态 | `1` 启用，`0` 禁用；前台只返回启用数据 |
| `create_time` | 创建时间 | 记录后台创建数据的时间 |
| `update_time` | 更新时间 | 记录最近一次修改时间 |
| `is_deleted` | 逻辑删除标记 | `0` 正常，`1` 已删除；删除接口只做逻辑删除 |

`section_key + sort_order` 的设计让首页可以按区块取数据，同时允许同一区块存在多条内容。例如 `hero` 可以只有一条主展示，也可以后续扩展成多张轮播；`workflow_entry`、`prompt_entry` 等区块可以按固定 key 被前端稳定识别。

### 2. award_record

`award_record` 用于保存项目获奖、成果、荣誉和展示记录。它单独建表，是因为获奖/成果信息有独立字段和独立列表，不适合混在普通首页区块里。

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `id` | 主键 ID | 数据库内部唯一标识，详情、修改、删除时使用 |
| `title` | 获奖/成果标题 | 前台列表和详情展示的主标题 |
| `award_level` | 奖项级别 | 例如校级、市级、国家级、院级、其他 |
| `issuer` | 颁发单位 | 用于说明奖项来源或成果发布单位 |
| `award_date` | 获奖/成果日期 | 用于时间展示和后续排序扩展 |
| `summary` | 摘要说明 | 展示该成果的简要背景和意义 |
| `image_url` | 图片 URL 或路径 | 第一版只保存字符串，占位展示用 |
| `link_url` | 详情链接 | 后续可指向新闻页、证明材料或前端详情页 |
| `sort_order` | 排序号 | 控制首页或成果列表展示顺序 |
| `status` | 启用状态 | 前台只返回启用数据 |
| `create_time` | 创建时间 | 记录创建时间 |
| `update_time` | 更新时间 | 记录最近修改时间 |
| `is_deleted` | 逻辑删除标记 | 删除时保留历史数据，不物理删除 |

## 三、首页内容区块与获奖记录的关系

`site_content` 和 `award_record` 没有外键关系。它们共同服务首页，但业务职责不同：

- `site_content` 负责首页结构性区块，例如 hero、项目介绍、模块入口、联系方式。
- `award_record` 负责获奖/成果列表，可在首页聚合接口中一起返回，也可以通过 `/api/awards` 单独查询。

这种拆分可以避免首页内容表变得过于混杂。首页区块偏展示配置，获奖记录偏成果档案，后续维护时分工更清楚。

## 四、接口说明

### 前台公开接口

前台接口允许匿名访问，OpenAPI 文档中不显示鉴权锁。

| 接口 | 方法 | 用途 | 返回数据 |
| --- | --- | --- | --- |
| `/api/site/home` | GET | 获取首页聚合数据 | hero、intro、模块入口、contact、sections、awards |
| `/api/site/contents` | GET | 查询首页内容列表 | 启用且未删除的 `site_content` 列表 |
| `/api/site/contents/{id}` | GET | 查询单条首页内容详情 | 单条 `site_content` |
| `/api/awards` | GET | 查询获奖/成果列表 | 启用且未删除的 `award_record` 列表 |
| `/api/awards/{id}` | GET | 查询单条获奖/成果详情 | 单条 `award_record` |

`/api/site/contents` 支持可选参数 `sectionKey`，例如：

```http
GET /api/site/contents?sectionKey=hero
```

`/api/site/home` 是前端首页最主要使用的接口。它把首页区块和获奖记录一次返回，避免前端首屏为了拼首页连续请求很多接口。

### 后台管理接口

后台接口需要 JWT + ADMIN 权限，必须先登录获取 token，并在文档页统一授权后调用。

| 接口 | 方法 | 用途 |
| --- | --- | --- |
| `/api/admin/site/contents` | POST | 新增首页内容 |
| `/api/admin/site/contents/{id}` | PUT | 修改首页内容 |
| `/api/admin/site/contents/{id}` | DELETE | 逻辑删除首页内容 |
| `/api/admin/awards` | POST | 新增获奖/成果记录 |
| `/api/admin/awards/{id}` | PUT | 修改获奖/成果记录 |
| `/api/admin/awards/{id}` | DELETE | 逻辑删除获奖/成果记录 |

## 五、权限与安全说明

首页展示接口是公开内容，用户未登录也应该能访问，因此 `SecurityConfig` 放行了：

- `GET /api/site/home`
- `GET /api/site/contents`
- `GET /api/site/contents/{id}`
- `GET /api/awards`
- `GET /api/awards/{id}`

后台管理接口仍然在 `/api/admin` 下，并通过 `@PreAuthorize("hasRole('ADMIN')")` 要求管理员角色。未带 token 请求后台接口会被 Spring Security 拦截。

`OpenApiConfig` 只做最小改动：前台首页接口不显示锁，后台管理接口仍显示统一授权要求。

## 六、设计说明

### 1. 为什么首页内容不写死在前端

如果首页标题、介绍、图片和链接都写死在前端，每次答辩、展示或正式上线前改文案都需要重新改前端代码、重新构建和部署。放到数据库后，管理员可以通过后台接口维护内容，前端只负责展示。

### 2. 为什么使用 section_key + sort_order

`section_key` 让程序稳定识别区块，`sort_order` 让同一区块内的多条内容可以调整顺序。不能依赖 `id` 排序，因为 `id` 只代表插入顺序，不代表业务展示顺序。

### 3. 为什么 award_record 单独建表

获奖/成果记录有奖项级别、颁发单位、日期、摘要等独立字段。如果把它塞进 `site_content.extra_json`，短期能展示，但后续查询、排序、维护和答辩说明都会变得不清晰。

### 4. 为什么第一版只保存 URL

当前后端主线目标是保证数据结构、前台展示和后台管理跑通，不引入外部存储和真实上传复杂度。后续需要正式上传时，可以在不改变展示接口大结构的前提下，把 URL 替换为真实文件服务返回的地址。

### 5. 为什么需要首页聚合接口

首页是高频首屏页面，如果前端分别请求 hero、intro、入口区块、awards，会增加接口数量和联调复杂度。`/api/site/home` 聚合这些数据，前端拿到后即可渲染首页。

## 七、当前测试数据说明

当前 `site_init_data.sql` 中的数据全部是测试/演示数据，不是最终定稿内容。包括：

- 首页标题、副标题、介绍文案
- 首页图片路径
- 模块入口跳转链接
- 获奖/成果标题、时间、颁发单位和摘要

正式展示前，建议团队根据最终项目名称、答辩材料、真实获奖情况和前端路由统一替换这些字段。

## 八、后续维护建议

1. 修改首页展示文案时，优先改 `site_content.title`、`subtitle`、`content`。
2. 调整首页展示顺序时，改 `sort_order`，不要依赖 `id`。
3. `section_key` 应保持稳定，前端通常会基于它识别页面区域。
4. 图片和链接正式上线前要替换为真实可访问地址。
5. 不建议物理删除首页内容或获奖记录，后台删除接口已经采用逻辑删除。
6. 如果后续要扩展首页轮播、团队成员、技术创新点，可以继续使用新的 `section_key`，不需要马上引入复杂 CMS。
