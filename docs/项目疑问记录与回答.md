# 项目疑问记录与回答

本文档记录当前对后端项目结构、业务流程、AI 接入方向、案例展示、复盘沉淀等问题的理解。回答基于当前仓库已有代码、SQL 和文档整理。

## 1. JWT 是什么？

JWT 全称是 JSON Web Token，可以理解为“登录凭证”。

在当前项目里，用户调用：

```http
POST /api/auth/login
```

登录成功后，后端会返回一个 `accessToken`。前端之后访问需要登录的接口时，要在请求头里带上：

```http
Authorization: Bearer <accessToken>
```

后端的 `JwtAuthenticationFilter` 会解析这个 token，确认是谁在访问、角色是什么。当前后台管理接口需要 `ADMIN` 角色，所以只有管理员 token 才能访问 `/api/admin/**`。

JWT 的作用主要有三个：

1. 证明用户已经登录。
2. 告诉后端当前用户是谁。
3. 告诉后端当前用户有什么角色权限，例如 `ADMIN`。

它不是密码本身，也不是数据库里的用户信息。它是登录成功后由后端签发的一段加密凭证。

当前项目里的 JWT 配置在：

- `src/main/resources/application.yml`
- `src/main/java/com/project/common/config/JwtProperties.java`
- `src/main/java/com/project/common/util/JwtUtil.java`
- `src/main/java/com/project/common/config/JwtAuthenticationFilter.java`

## 2. 案例展示现在是不是写死的？以后是否要动态收集用户工作流中生成的图片？复盘沉淀是否需要 AI 接入？

### 当前实现

当前“案例展示”不是写死在 Java 代码里，而是写在数据库初始化 SQL 里。

相关表：

- `case_project`
- `case_asset`

相关初始化文件：

- `sql/case_init_data.sql`

也就是说，现在案例数据是“预置演示数据”。它不是用户真实使用平台后自动产生的，也不是 AI 自动生成的。后端只是从数据库查出来返回给前端。

当前案例资源也只是 URL 或路径字符串，例如图片路径、PDF 路径。当前后端没有实现真实文件上传，也没有实现从用户工作流自动收集生成图片。

### 后续更合理的发展方向

如果项目后续要更像真实平台，案例展示可以从“预置案例库”逐渐升级为“用户成果沉淀库”：

1. 用户在平台工作流中完成某个阶段。
2. 用户使用平台内接 AI API 生成图片、文本、分析结果或方案材料。
3. 后端把这些生成结果保存为项目成果。
4. 用户选择是否把成果发布为案例。
5. 管理员审核后进入案例展示模块。

这样案例就不只是演示数据，而是用户真实工作成果。

### 复盘沉淀是否需要 AI 接入

复盘模块后续很适合接入 AI，但不一定必须完全由 AI 自动生成。

更合理的方式是：

1. 用户完成一个工作流或一个项目阶段。
2. 系统收集过程数据，例如使用了哪些工具、输入了哪些提示词、生成了哪些图片、遇到什么问题。
3. AI 根据过程数据生成一版复盘草稿。
4. 用户可以修改、补充、确认。
5. 最终保存为 `review_record`。

因此，复盘沉淀可以是“AI 辅助生成 + 用户确认修改”，而不是完全自动生成后不可编辑。

## 3. 用户视角完整流程中，首页聚合数据放什么？提示词、AI 平台、案例之间是什么关系？

### 首页聚合数据放什么

当前首页聚合接口是：

```http
GET /api/site/home
```

它返回 `HomeVO`，主要包括：

- `hero`：首页首屏标题、介绍、图片、按钮链接。
- `intro`：平台介绍。
- `workflowEntry`：工作流模块入口。
- `toolRecommendEntry`：AI 工具测评/推荐入口。
- `promptEntry`：提示词库入口。
- `caseEntry`：案例展示入口。
- `reviewEntry`：复盘沉淀入口。
- `contact`：联系方式或团队说明。
- `sections`：按 `sectionKey` 分组后的所有首页内容。
- `awards`：获奖/成果记录。

这些数据来自：

- `site_content`
- `award_record`

首页聚合数据本质上是“首页要展示的内容和模块入口”，不是具体业务数据本身。它更像前端首页的配置中心。

### 提示词库当前怎么用

当前项目第一版的提示词库是“提供提示词内容给用户复制使用”。

当前流程是：

1. 用户在平台选择设计阶段。
2. 用户查看该阶段推荐提示词。
3. 用户复制提示词。
4. 用户自己打开豆包、DeepSeek、Kimi、ChatGPT 等外部 AI 平台。
5. 用户把提示词粘贴进去生成内容。

也就是说，当前平台不直接替用户调用 AI API。

### 后续是否需要内接 API 来生成

如果项目继续升级，内接 AI API 是一个很自然的方向。

升级后的流程可以变成：

1. 用户选择阶段。
2. 用户选择提示词模板。
3. 用户在平台内修改提示词。
4. 用户选择 AI 工具或模型。
5. 后端调用对应 AI API。
6. 平台保存生成结果。
7. 生成结果进入案例、复盘或用户项目资产。

这时提示词库就不只是“复制文本”，而是“平台内生成能力的一部分”。

### 为什么案例放在提示词后面

从当前项目设计逻辑看，案例放在提示词后面是合理的，因为它对应用户学习和使用 AI 的顺序：

1. 先了解设计工作流。
2. 再知道这个阶段可以用哪些 AI 工具。
3. 再拿到适合这个阶段和工具的提示词。
4. 最后看别人或示例项目用这些方法做出了什么成果。

所以案例不是提示词的附属品，而是“方法使用后的成果展示”。

### 案例是不是用户成果？

从最终产品角度看，案例最好分两类：

1. 平台预置示范案例：用于演示、教学、答辩展示。
2. 用户真实成果案例：用户完成项目后沉淀出来，经审核后展示。

当前项目第一版用的是预置案例数据，偏演示案例。后续如果接入用户项目、文件上传、AI 生成结果保存，就可以把用户成果转化成真实案例。

## 4. DTO 是前端传给后端的请求吗？

基本可以这样理解：DTO 是“前端传给后端的数据结构”。

更准确地说，当前项目里的 DTO 主要用于接收请求体，也就是前端发来的 JSON。

例如新增工具时，前端请求：

```http
POST /api/admin/tools
Content-Type: application/json
```

请求体可能是：

```json
{
  "name": "DeepSeek",
  "code": "DEEPSEEK",
  "officialUrl": "https://www.deepseek.com",
  "description": "适合文本分析和方案推理",
  "status": 1
}
```

后端会用 `AiToolCreateRequest` 这个 DTO 接收。

DTO 的作用：

1. 定义前端需要传哪些字段。
2. 做参数校验，例如不能为空、不能小于 0、评分不能超过 10。
3. 避免前端直接操作数据库 Entity。

当前项目里的几个概念可以这样区分：

| 类型 | 方向 | 作用 |
| --- | --- | --- |
| DTO | 前端 -> 后端 | 接收请求参数 |
| Entity | 后端 -> 数据库 | 对应数据库表 |
| VO | 后端 -> 前端 | 控制接口返回字段 |

## 5. 现在里面的数据都是假的吗？之后需要自己做数据再存储进去吗？

当前大部分业务数据都是演示数据或初始化数据，不是最终真实业务数据。

例如：

- 工作流阶段和步骤是初始版本。
- AI 工具测评数据是演示测评。
- 提示词是预置示例。
- 案例是占位案例。
- 案例图片和资源路径是占位路径。
- 复盘记录是初始化演示记录。
- 首页文案和获奖记录是测试展示内容。

这些数据主要作用是：

1. 让项目跑起来。
2. 让前端能联调。
3. 让答辩或展示时有数据可看。
4. 验证数据库、接口、页面流程是否正确。

后续正式使用时，确实需要团队自己整理真实数据并存进去。

可以通过两种方式维护：

1. 直接改 SQL 初始化文件，适合开发早期和演示数据统一维护。
2. 通过后台接口新增/修改数据，适合后续做后台管理页面。

正式数据来源可以包括：

- 团队真实建筑设计流程。
- 真实 AI 工具测评结果。
- 团队整理的高质量提示词。
- 自己生成或整理的案例图片和文件。
- 用户真实使用后的复盘记录。
- 项目真实获奖、成果、团队介绍。

## 6. 项目进一步拓展可以做哪些模块？AI 工具测评模块调用 API 算一个吗？

AI 工具测评模块调用外部 API 算一个重要拓展，但它不是唯一方向。

当前项目第一版是“内容展示 + 管理维护 + 工具导航”。进一步升级可以分几类。

### 1. AI API 接入

这是最明显的拓展。

可以做：

- 接入文本生成模型，例如 DeepSeek、通义、Kimi、ChatGPT。
- 接入图像生成模型。
- 接入多模型对比，同一个提示词发送给多个模型。
- 保存每次生成记录。
- 保存生成图片、生成文本、模型参数、提示词版本。

这会让平台从“推荐用户去外部 AI 平台”升级为“平台内直接生成”。

### 2. 用户项目空间

当前没有完整的“我的项目”概念。后续可以新增：

- 用户项目表。
- 项目阶段进度。
- 项目下的提示词使用记录。
- 项目下的 AI 生成结果。
- 项目资源文件。
- 项目复盘。

这会让系统从展示型平台升级为工作台型平台。

### 3. 文件上传和资源管理

当前案例和复盘资源只保存 URL 字符串。后续可以新增：

- 本地文件上传。
- 文件类型校验。
- 文件大小限制。
- 图片预览。
- 文件访问路径映射。
- 对象存储，例如 OSS、MinIO、七牛云。

### 4. 复盘自动生成

后续可以让 AI 根据用户工作过程生成复盘草稿：

- 使用过哪些阶段。
- 使用过哪些提示词。
- 调用了哪些 AI 工具。
- 生成了哪些结果。
- 用户修改了什么。
- 最终形成了什么成果。

然后 AI 总结问题、方案、经验和建议。

### 5. 案例自动沉淀

用户项目完成后，可以一键生成案例：

- 项目基本信息。
- 过程图片。
- 成果图片。
- 使用工具。
- 使用提示词。
- 设计说明。
- 复盘总结。

管理员审核后进入案例展示模块。

### 6. 后台管理系统完善

当前后端已有很多后台接口，但还可以继续完善：

- 后台列表接口。
- 分页查询。
- 批量排序。
- 批量启用/禁用。
- 操作日志。
- 角色权限细分。

### 7. 数据统计和可视化

可以统计：

- 哪些阶段访问最多。
- 哪些工具被推荐最多。
- 哪些提示词复制最多。
- 用户最常用哪些模型。
- 哪类案例最受欢迎。
- 复盘中高频问题是什么。

### 8. 推荐算法

第一版推荐主要是人工维护关系。后续可以根据用户行为做推荐：

- 按阶段推荐工具。
- 按工具推荐提示词。
- 按用户项目类型推荐案例。
- 按历史使用记录推荐下一步操作。

## 7. 复盘阶段按理来说是用户做完整个流程之后自动生成的吗？也可以用户自己写吗？它到底是什么？

复盘可以理解为“项目完成后或阶段完成后，对整个过程的经验总结”。

它不是必须只有一种生成方式。更合理的是支持三种方式。

### 方式一：用户自己写

这是最简单、最容易落地的方式。

用户填写：

- 项目名称。
- 使用阶段。
- 使用工具。
- 遇到的问题。
- 解决方案。
- 最终效果。
- 经验反思。
- 附件图片或文件。

这种方式不依赖 AI，适合第一版。

### 方式二：AI 自动生成草稿，用户修改确认

这是后续比较理想的方式。

系统收集用户过程数据后，AI 自动生成：

- 本次流程总结。
- 使用工具总结。
- 提示词使用总结。
- 成果亮点。
- 问题和不足。
- 后续建议。

然后用户可以编辑这份草稿，确认后保存。

这种方式比较符合“AI 辅助设计决策平台”的定位。

### 方式三：系统自动生成基础记录

即使不接 AI，系统也可以自动生成一部分结构化记录，例如：

- 用户完成了哪些阶段。
- 用了哪些工具。
- 复制过哪些提示词。
- 上传了哪些成果。
- 哪些内容被保存为案例。

这类记录偏“过程日志”，还不是完整复盘，但可以作为 AI 生成复盘的材料。

### 当前项目实际情况

当前代码中的复盘模块更接近“管理员维护的复盘展示内容”：

- 前台可以公开查询复盘列表和详情。
- 后台管理员可以新增、修改、删除复盘。
- 当前没有普通用户自己提交复盘的接口。
- 当前没有 AI 自动生成复盘。
- 当前没有和用户真实工作流过程打通。

所以当前它是“复盘内容展示与管理模块”，不是完整的“用户完成流程后自动复盘系统”。

后续如果继续开发，可以把它升级为：

```text
用户工作流过程记录
  -> AI 生成复盘草稿
  -> 用户编辑确认
  -> 保存复盘
  -> 可选择发布为案例或经验沉淀
```

## 总结

当前项目第一版主要是一个“可展示、可维护、可联调”的后端基础平台。它已经有工作流、工具、提示词、案例、复盘、首页内容这些模块，但大部分数据是预置演示数据，AI 生成、用户项目空间、自动复盘、真实案例沉淀还没有真正打通。

后续真正做深以后，项目的核心升级方向应该是：

1. 接入 AI API，让用户在平台内生成内容。
2. 建立用户项目空间，记录每个用户的设计流程。
3. 保存 AI 生成结果，包括文本、图片、文件。
4. 自动或半自动生成复盘。
5. 将优秀用户成果沉淀为案例。
6. 完善后台管理、文件上传、统计分析和推荐能力。
